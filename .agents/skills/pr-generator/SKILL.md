# PR 생성 가이드 (pr-generator)

현재 작업 공간의 Git 변경 사항과 사용자-에이전트 대화 맥락을 근거로 PR 문서를 작성한다. 추측으로 변경 의도를 만들지 않는다.

## 작업 절차

1. `git status --short`, 현재 브랜치, 기본 브랜치와의 merge-base를 확인한다. 기본 브랜치가 `main`이 아니면 저장소의 기본 브랜치를 사용한다.
2. `git diff --stat`, `git diff <base>...HEAD`, 필요 시 작업 트리 diff를 읽어 실제 변경 파일과 검증 상태를 파악한다.
3. 대화 맥락에서 Why를 추출한다. 근거가 없으면 사용자가 PR 의도 또는 제목을 지정하지 않은 경우에만 짧게 질문한다.
4. 변경의 의존 관계를 보고 **리뷰 확인 순서**를 잡는다. 계약·스키마 → 핵심 로직 → 연결부(러너/CLI) → 테스트·문서 순을 기본으로 하되, 이번 diff에 맞게 조정한다.
5. 아래 형식의 Markdown을 작성한다. 사용자에게 제목을 받지 못했으면 변경 내용에서 간결한 제목을 정한다.
6. 사용자가 PR 문서 파일을 요청했거나 기본 산출물을 원하면 `pr-docs/MM-dd-{PR 제목}.md`에 저장한다. 채팅용 초안만 요청한 경우에는 파일을 만들지 않는다.

## PR 문서 형식

생성되는 PR 문서는 반드시 다음 순서로 4가지 핵심 섹션을 포함해야 합니다. **확인 순서가 맨 앞**이다.

### 확인 순서

- PR 본문 최상단에 둔다. 리뷰어가 파일을 어떤 순서로 보면 이해가 빠른지 제안한다.
- 번호 목록으로 3~7단계 정도만 쓴다. 파일을 전부 나열하지 말고, **먼저 볼 진입점**과 **이어서 볼 묶음**만 고른다.
- 각 단계는 `` `경로` `` + 한 줄 이유(무엇을 확인하면 되는지)로 쓴다.
- 테스트·문서는 핵심 동작을 이해한 뒤로 미룬다. 기계 생성물·락파일·포맷만 바뀐 파일은 생략하거나 맨 끝에 “스킵 가능”으로 표시한다.
- 예:

```markdown
## 확인 순서

1. `app/evaluation/service_growth_contracts.py` — 입출력 계약부터 보면 이후 모듈 역할이 읽힌다
2. `app/evaluation/absolute_judgment.py` → `service_growth_generation.py` — 절대 채점·생성 핵심
3. `app/evaluation/run_service_growth_eval.py` — 한 회차가 끝까지 도는 연결
4. `tests/unit/evaluation/` — 위 계약을 고정하는 테스트
5. `tests/evaluation/service_growth_cases.json` — 수치 사례 fixture (원하면)
```

### PR 개요

- 불릿 리스트로 변경 배경·의도와 핵심 결과를 제시한다.
- 불필요한 수식이나 추상적 표현을 피하고, 결과를 검증 가능한 사실로 쓴다.

### 주요 변경 파일

- PR 플랫폼에서 동작하는 인라인 코드 경로(예: `` `app/service.py` ``)를 사용한다. 로컬 IDE 링크가 필요한 문맥에서만 절대 경로 Markdown 링크를 추가한다.
- 파일별 배경과 핵심 역할을 한 문장으로 적는다.
- 확인 순서에 이미 나온 파일이라도, 여기서는 역할 요약용으로 다시 적어도 된다.

### 비고

- 실제로 확인한 테스트·린트 명령과 결과를 적는다. 실행하지 않은 검증은 실행한 것처럼 쓰지 않는다.
- 환경 변수, 의존성, 마이그레이션, 호환성 제약, 후속 작업처럼 리뷰어가 알아야 할 사항만 포함한다.

## 문체

- 간결한 개조식·명사형 종결을 사용한다. “~ 구현하였습니다” 대신 “~ 추가”로 쓴다.
- 한 항목에는 하나의 변경만 담고, 불확실한 내용은 사실과 추론을 구분해 쓴다.
