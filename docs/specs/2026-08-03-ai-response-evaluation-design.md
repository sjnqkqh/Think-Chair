# AI 응답 평가 체제 설계

- 작성일: 2026-08-03
- 상태: 설계 확정, 구현 계획 작성 완료 (`docs/plans/agentic-research-rag/08-ai-response-evaluation.md`)
- 관련: `docs/specs/2026-07-29-product-aligned-rag-evaluation-design.md`, `docs/plans/agentic-research-rag/07-evaluation-continuation.md`

## 1. 목적

문서 생성 후 DeepSeek로 돌리는 **문서 평가**와 별개로, **AI 대화 응답**을 평가하는 체제를 만든다.

지금 단계는 실제 서비스에 점수를 붙이지 않는다. 개발할 때 같은 상황에서 “지금 방식 답”과 “근거를 참고한 답”을 비교해, 근거를 붙인 쪽이 실제로 나은지 판단할 성적표를 만든다. 다만 핵심 로직은 나중에 실제 응답 평가·로깅으로 확장할 수 있도록 메인 코드(`app/`)에 둔다.

## 2. 문서 평가와의 차이

| | 문서 평가 (기존) | AI 응답 평가 (이번) |
|---|---|---|
| 대상 | 생성된 원고 | 대화 중 AI 응답 |
| 목적 | 체크리스트·대화 반영도 | 근거 활용이 답을 더 낫게 만드는지 |
| 방식 | 단일 점수·등급 | 규칙 검사 + 두 답 나란히 비교 |
| 위치 | `app/graph` / `app/services` | `app/evaluation/` (분리) |

두 평가는 기준이 다르므로 코드·프롬프트·결과 형식을 공유하지 않는다.

## 3. 범위

### 포함

- 개발용으로 돌리는 AI 응답 비교 평가
- 같은 입력에서 **지금 방식 답**과 **근거를 참고한 답** 생성·비교
- 응답 형태가 수치·근거 제시든 추가 질문이든 **모두 평가 대상** (형태별 사전 분류기 없음)
- 규칙 검사(치명 실수)와 LLM 나란히 비교
- 사람이 읽는 요약 + 기계용 결과 파일
- 판정 LLM을 설정으로 교체할 수 있는 구조 (첫 구현은 일반 LLM API)

### 제외 (지금)

- 실제 사용자 대화에 대한 실시간 점수 저장·화면
- 문서 평가 흐름 변경
- 출처 본문과 인용 문장의 내용 일치 검사 (2단계로 미룸)
- Cursor IDE 구독/SDK를 판정기로 사용
- “승률 N%면 통과” 같은 숫자 게이트 확정 (첫 비교 결과를 본 뒤 정함)

## 4. 평가 흐름

한 사례마다:

1. 평가용 예시 대화(AI 질문 + 사용자 답변)를 읽는다.
2. 답을 두 개 만든다.
   - 지금 방식: 근거 검색 없이 생성
   - 근거 참고: 준비된 평가용 자료(또는 이후 실제 검색 결과)를 참고해 생성
   - 답이 설명형이든 질문형이든 그대로 받는다.
   - 첫 구현에서는 완성된 Agentic RAG 전체가 없어도, 평가용으로 미리 준비된 근거만으로 “근거 참고 답”을 만들 수 있어야 한다.
3. 규칙으로 먼저 검사한다. 실패면 해당 사례는 치명 실수로 기록한다.
4. LLM이 두 답을 나란히 비교한다.
   - 기준: 구체성, 대화 자연스러움, 주장 정확성
   - 답 순서만 바꿔 한 번 더 평가하고, 결과가 뒤집히면 무승부/불안정으로 기록한다.
5. 사례별·전체 요약 리포트로 남긴다.

## 5. 판정 기준

### 규칙 검사 (코드로 확정)

1단계(지금):

- 답변이 가리킨 출처 ID/URL이 실제 검색·허용 목록에 있는가
- 금지 출처·다른 사용자 자료를 노출하지 않았는가
- 출처 표시만 있고 연결 대상이 없는 유령 출처가 아닌가
- 출처를 인용했다면 해당 페이지 URL을 `cited_urls`와 본문 모두에 넣어, 사용자가 직접 열어 확인할 수 있는가

2단계(나중):

- 인용한 내용이 출처 본문과 실제로 맞는지

### LLM 나란히 비교

- 구체성: 막연한 말 대신 수치·사례·근거로 구체화했는지
- 대화 자연스러움: 근거 때문에 대화가 끊기거나 어색한 보고문이 되지 않았는지
- 주장 정확성: 틀린 사실·과장·근거 없는 단정을 덜 했는지

출처를 “잘 썼는지”의 존재·허용 여부는 규칙 검사에 두고, LLM 비교 점수로 대체하지 않는다.

### 통과 기준

- 지금 고정: 치명 실수 0건
- 보류: 승률·항목별 비율 숫자는 첫 실행 결과를 본 뒤 확정

## 6. 배치

핵심 로직은 메인에 두되, 채팅·문서 생성 코드와 섞지 않는다.

```
app/evaluation/                 # 응답 비교 평가 전용 (실제 응답 평가 확장 예정)
  response_comparison_contracts.py  # 입력·결과 형식
  citation_allowance.py             # 출처 존재·허용 규칙 검사
  response_comparison.py            # LLM 나란히 비교
  case_response_comparison.py       # 사례 단위 생성·검사·비교
  comparison_report.py              # 집계·리포트
  run_response_comparison.py        # 개발용 실행기

tests/evaluation/               # 예시 대화·평가용 자료
scripts/run_ai_response_comparison.py
tests/unit/evaluation/          # 형식·규칙 단위 테스트
```

문서 평가(`evaluate_document`)는 현재 위치를 유지한다.

## 7. 리포트

### 사례마다

- 두 답 원문
- 규칙 검사 통과/실패 사유
- 비교 결과: 승 / 패 / 무승부(순서 뒤집힘)
- 짧은 판정 이유 (어느 기준에서 갈렸는지)

### 전체 요약

- 치명 실수 건수
- 승·무·패 개수와 비율
- 항목별 승률 (구체성 / 자연스러움 / 정확성)
- 순서 변경 시 판정 뒤집힘 비율

관리자 화면은 만들지 않는다. 파일로 저장한다.

## 8. 판정 모델

- 답 생성 모델과 판정 모델을 분리할 수 있어야 한다.
- 첫 구현은 일반 LLM API로 호출한다. (Cursor SDK 비사용)
- 모델 ID는 설정으로 교체 가능하게 둔다.
- 관례상 판정은 생성보다 상위 모델을 쓰는 것을 권장하되, 구체 모델은 구현 시 환경에 맞게 고른다.

## 9. 기존 Agentic RAG 평가와의 관계

- PR 00의 예시 대화 schema·corpus 계약은 입력 데이터로 재사용할 수 있다.
- 검색 적중(Recall 등)은 이 설계의 주 목표가 아니다. 필요하면 옆에서 따로 집계하고, 응답 비교 성적표와 결과를 섞지 않는다.
- RAG 기능 확대(추가 조사·비동기 연결 등)는 이 응답 비교에서 치명 실수 0과, 이후 정할 승률 기준을 본 뒤에 진행한다.

## 10. 성공 정의

이 설계의 구현이 성공하려면:

1. 문서 평가 코드를 바꾸지 않고도 AI 응답 비교를 돌릴 수 있다.
2. 규칙 실패와 LLM 비교 결과가 사례별·전체 리포트로 남는다.
3. 응답이 질문형이든 설명형이든 같은 파이프라인으로 평가된다.
4. 판정 모델을 설정만으로 바꿀 수 있다.
5. 나중에 실제 응답 평가를 붙일 때 `app/evaluation/` 계약을 재사용할 수 있다.
