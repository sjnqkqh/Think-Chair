# Agentic RAG 사전 결정 사항

[전체 계획](README.md) · [PR 실행 계획](prs/README.md)

구현 전에 정해야 하는 항목만 모은다. 실제 서비스 비용·호출 제한처럼 측정이 필요한 운영값과, PR 진행 여부를 판단하기 위한 평가 게이트를 구분한다.

각 결정의 **선택** 문장은 사용자와 제품에 생기는 변화를 일상 언어로 설명한다. 구현 용어는 그 아래 계약에서만 사용한다.

## 상태

- `DECIDED`: 결정 완료
- `PARTIAL`: 방향은 정했지만 수치나 운영 규칙이 남음
- `OPEN`: 해당 PR을 시작하기 전에 결정 필요
- `DEFERRED`: 지금은 미루되 후속 PR 전에는 결정 필요

## 한국어·영어 자료를 함께 다루는 방법

### 저장

- 한국어·영어 원문을 번역하지 않고 같은 자료 저장소에 넣는다.
- 제목·문단·목록·표·코드 블록 같은 문서 구조를 우선 보존하고, 임베딩 모델이 받을 수 있는 최대 길이에 맞춰 문서를 나눈다.
- 언어 때문에 문단을 분리하지 않는다.
- 나눈 조각에는 `language: ko | en | mixed | und`를 기록하되, 기본 검색에서 특정 언어만 고르는 용도로 사용하지 않는다.
- 하나의 저장소 묶음에는 같은 임베딩 모델·버전·차원과 같은 문서 분할 규칙만 사용한다.
- 임베딩 모델이나 문서 분할 규칙이 바뀌면 기존 자료와 섞지 않고 새 저장소에 다시 넣는다.

### 검색

1. 사용자의 원문 검색어를 한국어·영어를 함께 처리하는 같은 임베딩 모델로 한 번 검색한다.
2. 한국어와 영어 문서 조각을 같은 검색 결과 후보로 받는다.
3. 근거가 부족하면 PR 05의 제한된 웹 조사로 넘긴다.
4. 원문과 인용은 원래 언어를 유지하고, 설명만 사용자 언어로 생성한다.

### 선택 전 평가

임베딩 모델을 고르기 전에 한국어 질문으로 한국어·영어 자료를 찾는 경우와 영어 질문으로 영어·한국어 자료를 찾는 경우, 두 언어가 섞인 질문을 모두 측정한다. 기준을 통과하면 번역이나 자료 중복 저장을 추가하지 않는다. 부족할 때는 먼저 모델을 다시 고르고, 번역이나 여러 검색어 사용은 그다음 별도 실험으로 평가한다.

## D1. 검색·원문 수집 계약 — `OPEN`

**결정 시점:** PR 01 전

- 검색 API, 비동기 HTTP 요청 도구, HTML 본문 추출 도구
- 호출량, 호출 속도, 제한 시간, 동시 요청 수, 최대 검색 결과 수와 응답 크기
- robots.txt 처리, 검색 서비스와 출처의 이용약관 확인

**결정 결과:** 사용할 서비스, 호출 제한값, 서비스 오류를 내부 오류로 바꾸는 규칙.

## D2. 임베딩 모델·벡터 저장소 — `OPEN`

**결정 시점:** PR 02 전

- 다국어 평가를 통과한 임베딩 모델·버전·차원
- 벡터 저장소와 사용자별 자료를 구분하는 기능
- 공용 자료와 현재 사용자의 비공개 자료만 안전하게 함께 찾는 저장 구조
- 모델과 문서 분할 규칙이 다른 자료가 섞이지 않게 저장소를 나누는 방법
- 평가로 정한 문서 조각의 크기·겹침 범위·길이 계산 방식
- 검색 인덱스를 다시 만드는 방법과 이전 인덱스로 되돌리는 방법

임베딩 모델과 버전은 사용자가 요청마다 고르는 값이 아니라, 앱을 배포할 때 정하는 설정이다.

## D3. 자료의 소유권·보존 기간 — `PARTIAL`

**결정 시점:** PR 02 전

확정된 기본 경계:

- 공개 웹 원문과 문서 조각은 모든 사용자가 공유하는 저장소에서 중복을 제거한다.
- 어떤 조사·질문·원고가 어떤 자료를 사용했는지는 사용자별 비공개 기록으로 남긴다.
- 사용자 업로드, 대화, 인증이 필요한 URL과 비공개 URL은 사용자별 저장소로 분리하고 다른 사용자가 검색하지 못하게 한다.
- 원고를 삭제하면 해당 원고와의 연결 기록과 비공개 자료는 삭제하지만, 공용 웹 자료는 삭제하지 않는다.
- 자동 안전검사를 통과한 공개 웹 자료는 수집 직후 공용 검색에 포함한다.
- URL별로 처음 안전하게 수집한 원문·문서 조각·벡터 하나만 저장한다.
- 검색 결과 URL이 이미 저장된 canonical URL 또는 URL 별칭과 일치하면 `fetch_page`를 호출하지 않고 기존 자료를 재사용한다.
- 처음 보는 URL만 수집한다. redirect와 canonical URL을 확인한 뒤 이미 저장된 자료로 판명되면 새 원문·문서 조각·벡터를 만들지 않고 URL 별칭만 연결한다.
- 같은 URL의 내용이 나중에 바뀌었는지 자동 확인하거나 갱신하지 않는다.
- 최신 정보가 중요한 질문에서 저장 자료의 발행일·수집일이 충분하지 않으면 같은 URL을 다시 수집하지 않고 더 최근의 다른 출처를 찾는다.
- 삭제되었거나 정책을 위반한 자료는 원문·문서 조각·벡터와 URL 별칭에서 삭제하고 다시 검색되지 않게 한다.

남은 결정:

- `document_id`, `chunk_id` 생성 규칙
- 서로 다른 문서를 합치지 않는 보수적인 URL 정규화·별칭 규칙
- 현재 원문의 보존 기간
- robots.txt·라이선스·이용약관을 위반한 자료의 저장·삭제 규칙

첫 버전은 같은 URL의 변경을 추적하지 않는다. 이 때문에 저장 후 같은 URL에서 수정된 내용은 반영되지 않을 수 있으며, 과거 답변의 원문을 별도로 보존하거나 재현하지도 않는다.

## D4. 비동기 결과 전달 계약 — `DECIDED`

**선택:** 조사는 뒤에서 계속하고, 화면이 상태를 주기적으로 확인해 완료 표시만 한다

- 현재 턴에는 근거 없는 사실 주장을 피하고 개념적 질문·가정으로 대화를 이어간다.
- 기존 채팅 API는 실시간 전송 방식(SSE)으로 현재 턴의 답변을 계속 보낸다.
- 채팅 화면이 `research_required` 신호를 받으면 별도 조사 생성 API인 `POST /api/research/jobs`를 호출한다.
- 조사 생성 API는 요청을 접수했다는 HTTP `202 Accepted`와 변하지 않는 작업 ID, 상태 확인 주소를 반환하고 조사를 뒤에서 실행한다.
- 같은 메시지로 요청이 겹쳐도 조사 작업은 하나만 생성한다.
- 채팅 화면은 상태 확인 주소를 주기적으로 조회하고, 완료되면 `근거 준비됨`만 표시한다.
- 완료된 근거로 현재 답변을 수정하거나 자동 후속 메시지를 보내지 않는다.
- 다음 사용자 턴부터 완료된 근거를 자동 사용한다.
- 앱 재시작으로 중단된 job은 `failed/restart_interrupted`로 표시한다.
- 작업 상태와 결과는 해당 사용자와 원고의 소유권을 확인한 뒤에만 보여준다.

## D5. 근거가 충분한지와 검색 확대 계약 — `DECIDED`

**선택:** 핵심 주장에 믿을 만한 근거가 있으면 답하고, 덜 중요한 빈틈은 함께 알린다

`EvidenceSufficiency`

- `sufficient: bool`
- `missing_aspects: list[str]`
- `supporting_chunk_ids: list[str]`
- `reason_code: str`

핵심 주장과 직접 관련된 자료가 있고 출처와 인용이 유효하며, 발행일·수집일이 질문의 시점에 맞아야 근거가 충분하다고 판단한다. 덜 중요한 설명의 근거가 비어 있으면 그 부분을 `missing_aspects`로 알리고 대화를 이어갈 수 있다. 벡터 저장소마다 검색 점수의 의미가 다르므로 평가 전에 공통 점수 기준을 임의로 정하지 않는다.

근거가 충분한지는 작업 성공 여부와 별도로 판단한다. 검색 자체는 정상적으로 끝났지만 근거가 부족한 경우를 시스템 오류로 취급하거나 자동 재시도하지 않는다.

기본 흐름:

```text
공용 자료와 현재 사용자의 비공개 자료 검색
→ 근거가 충분하면 웹 검색 생략
→ 부족하면 PR 05의 제한된 웹 조사 실행
→ 정해진 시간·횟수를 모두 사용해도 부족하면 확인된 내용만 답하거나 답변 보류
```

## D6. 중복 실행·재시작·복구 계약 — `DECIDED`

**선택:** 같은 작업이 겹쳐도 중복 저장되지 않게 하되, 앱 재시작으로 끊긴 조사는 다시 살리지 않는다

- 조사 작업 ID와 각 저장 단계의 키를 묶어 같은 작업이 중복 저장되지 않게 한다.
- 메인 대화와 조사 실행기가 각각 어떤 상태를 소유하는지 구분한다.
- 여러 검색 결과를 동시에 처리한 뒤 합치는 규칙을 정한다.
- 중간 진행 상태는 저장 가능한 형태만 사용한다.
- `queued → running → completed | partial | failed | cancelled` 전이
- 다시 시도할 오류와 즉시 끝낼 오류, 한 작업 안에서 허용할 재시도 횟수를 정한다.
- URL 등록, 원문 수집, 벡터 저장, 결과 전달이 중복 실행되어도 결과가 하나만 남게 한다.
- 앱 시작 시 끝나지 않은 작업을 찾아 `failed/restart_interrupted`로 정리한다.
- 앱 종료 때는 정해진 유예 시간까지만 기다리고 남은 작업을 `failed/shutdown_interrupted`로 끝낸다.
- 사용자가 취소하면 실행을 멈추고 `cancelled/user_cancelled`로 기록한다.
- 제한 시간을 넘으면 실행을 멈추고 `cancelled/deadline_exceeded`로 기록한다.
- 저장된 진행 상태와 코드·자료 구조 버전의 호환 규칙을 정한다.
- 같은 입력에 같은 결과가 나와야 하는 검색·수집 단계와 LLM이 판단하는 단계를 구분한다.

LangGraph는 중단된 작업을 다시 시작할 때 일부 단계를 재실행할 수 있다. 따라서 네트워크 요청과 DB·벡터 저장은 같은 단계가 반복되어도 중복 결과를 만들지 않게 설계한다. 조사 작업끼리 진행 상태가 섞이지 않도록 분리하는 것도 필수다.

첫 버전에는 서버 재시작 후 작업을 자동 복구하는 별도 시스템을 두지 않는다. 사용자가 질문을 다시 입력하면 새 조사 작업으로 처음부터 실행하며 재시도 버튼도 제공하지 않는다.

## D8. 운영 기록·개인정보·비용 계약 — `PARTIAL`

**선택:** 원문은 남기지 않고 작업 단계·시간·비용처럼 운영에 필요한 기록만 남긴다

- 요청·작업·실행 단계·도구·자료·인용을 서로 연결해서 추적할 수 있는 ID
- 단계별 소요 시간, 재시도, 상태, 도구 호출, 토큰과 외부 서비스 비용
- 검색된 문서 조각 ID와 점수, 근거 충분 여부, 모델·프롬프트·검색 인덱스 버전
- 사용자 질문, 원문, 답변 전문은 기본 운영 기록에 저장하지 않음
- API 키, 쿠키, 인증 정보, 원문 전체는 로그에서 제외
- 비용 초과, 같은 작업 반복, 실패율 증가를 알릴 기준

PR 04에서 사용자 기능에 반영하지 않고 측정만 하는 동안의 운영 기록은 7일 보존한다. 실제 운영 기록의 보존 기간과 조사 한 건당 비용 한도는 외부 서비스 비용과 실제 조사 실행 결과를 확인한 뒤 확정한다.

## D9. 보안·공용 자료 등록 계약 — `DECIDED`

**선택:** 자동 안전검사를 통과한 웹 자료만 공용 검색 자료로 즉시 공유한다

- HTTP와 HTTPS 주소만 허용한다. 최초 접속과 주소 이동 때마다 내부망·현재 기기·클라우드 관리용 주소를 차단한다.
- 웹에서 가져온 본문은 AI에게 내리는 지시가 아니라 신뢰하지 않은 참고 자료로만 전달한다.
- 조사 도구는 읽기만 가능하며, 정해진 검색 횟수·자료 수·시간 안에서만 호출한다.
- 자료를 공용으로 저장할지, 사용자 전용으로 저장할지, 거부할지는 LLM이 아니라 서버의 안전 규칙이 결정한다.
- 출처를 식별할 수 없거나 주소·본문 안전검사를 통과하지 못한 자료는 공용 저장소에 넣지 않는다.
- HTML에서 스크립트, 스타일, 숨겨진 요소, 반복되는 메뉴와 안내 문구를 제거한다.
- 본문이 비었거나 너무 짧고, 문서 형식이 맞지 않거나, 대표 URL·제목이 없으면 거부한다.
- AI나 도구의 행동을 지시하는 문장은 문서 조각에서 제외하고, 참고할 사실이 남지 않으면 자료 전체를 거부한다.
- 안전검사를 통과한 자료도 LLM에는 신뢰하지 않은 참고 자료로 표시한다.
- 웹 요청에 로그인 정보, 쿠키, 인증 헤더를 전달하지 않는다.
- 조사 작업의 상태 확인·결과 조회·취소는 해당 사용자만 할 수 있다.
- 비공개 자료를 삭제할 때는 DB 원문, 벡터 저장소, 진행 상태 기록에서도 함께 삭제한다.
- 공용 자료가 정책을 위반하면 검색에서 제외하고 다시 수집하지 않는다.
- 저장 위치는 서버가 생성한 키로 정하며, 외부 URL이나 경로를 그대로 사용하지 않는다.
